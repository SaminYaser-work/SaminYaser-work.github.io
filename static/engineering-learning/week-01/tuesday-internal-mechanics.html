Make the claim atomic

Use a uniqueness constraint and one database transaction so exactly one concurrent attempt owns the protected mutation and valid replays recover its result.

01

The key names; the transaction gates

An idempotency key provides identity. Correctness comes from atomically coordinating ownership of that identity with the protected business mutation.

Two workers may receive the same merchant-scoped key at nearly the same time. A preceding “check whether the key exists” is not enough: both workers can observe absence before either writes. That is a check-then-act race.

A database uniqueness constraint on (scope, key) becomes the arbiter. Exactly one insert can win. For a short mutation whose idempotency row and business effect share one database, the owner creates both the effect and its replay result inside one transaction.

Mental model: the key says “which operation?” The uniqueness constraint says “which transaction owns it?” The shared commit says “the effect and replay record become durable together.”

03

Two attempts, one owner

The owner is whichever transaction successfully inserts the unique key row; arrival order does not guarantee ownership.

Canonicalize the protected input and compute its fingerprint.

Inside one transaction, attempt to insert (scope, key, fingerprint).

The successful insert owns the operation. It creates the charge and stores the COMPLETED outcome before committing once.

A conflicting attempt waits for the owner transaction to resolve, then reloads the record.

After owner commit, matching input receives the stored outcome. After rollback, no committed claim remains and the waiter can retry the insert.

04

Why one transaction matters

The uniqueness constraint removes the check-then-act race. The shared transaction closes another failure window: the charge must not commit without a durable record that tells future retries what happened.

  • Before commit: another transaction normally cannot observe the owner’s uncommitted intermediate row; it waits on the uniqueness conflict.
  • Owner commits: the waiter reloads COMPLETED, verifies the fingerprint, and returns the stored result.
  • Owner rolls back: neither the key claim nor charge is committed; the waiter can claim the key.
  • Fingerprint mismatch: reject the same-key/different-input request rather than replaying or mutating.
Good fit: short work where both the protected effect and idempotency record live in the same database.
Different design required: long-running operations or external side effects cannot remain inside one short local transaction. They need durable work state and explicit recovery.
05

Visible IN_PROGRESS and crash recovery

A separately committed IN_PROGRESS reservation lets a short request hand off long-running work, but it introduces stale ownership and ambiguous-effect recovery.

Do not use age alone to declare an owner dead and blindly repeat an effect. Store an owner or attempt token and a lease expiry. A replacement worker may take over only through an atomic compare-and-swap update that proves it owns the current lease state.

If a crash may have occurred around an external effect, the replacement must reconcile before repeating it:

  1. Reuse the same downstream idempotency key, or
  2. Query the provider for the operation’s status, then
  3. Complete local state from the discovered outcome.
Safety boundary: if the external system offers neither stable idempotency nor a status lookup, automatic recovery cannot prove that repetition is safe. Stop for manual reconciliation rather than risk duplicating the effect.
06

Questions

Answer in Telegram or chat in this order.

  1. Active exercise: Attempts A and B arrive together with the same key and fingerprint. What database mechanism arbitrates between them?
  2. Active exercise: Which attempt becomes the owner?
  3. Active exercise: What happens to B while A’s transaction remains uncommitted?
  4. Active exercise: What does B do after A commits?
  5. Active exercise: What can B do after A rolls back?
  6. Senior judgment: Would you keep a short charge-record creation entirely inside one transaction, or first commit a visible IN_PROGRESS reservation? Defend the choice using transaction duration, whether the side effect shares the database, concurrent-client behavior, and crash-recovery complexity.
