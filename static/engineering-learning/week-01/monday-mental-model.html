Identity before retries

Distinguish a logical operation from a transport attempt, then use a stable idempotency key to make an ambiguous retry safe.

01

The protected unit is the business intent

A retry is not “the same request” merely because its JSON looks the same. It is the same logical operation only when the caller carries one stable identity across every transport attempt.

The logical operation is the caller’s intended mutation, independent of network attempts—for example, “charge this checkout exactly once.” An idempotency key names that operation. Within a declared scope, the server binds the key to one canonical request and one durable outcome.

A timeout describes the caller’s knowledge, not the server’s commit state. The mutation may have failed before execution, may still be running, or may already have committed before the response was lost.

Key distinction: transport attempts are repeated client requests. Database lookups of the key are server-side mechanics; they are not the attempts being protected.
02

Essential terminology

Logical operationThe intended business mutation, independent of transport attempts.
Idempotency keyStable caller-supplied identity for one logical operation.
ReplayA repeated attempt using the same operation key.
Canonical requestThe protected input originally bound to the key.
Stored outcomeThe response or durable result returned on a valid replay.
Ambiguous outcomeThe caller cannot determine whether the server committed.
ScopeThe namespace where a key is unique, such as merchant + endpoint.
Retention windowHow long the server remembers the key and result.
03

The request sequence

The stable key connects two transport attempts to one logical operation.

The client chooses one key for one intended mutation and reuses it only when retrying that mutation.

The server interprets the key within an explicit namespace, such as merchant account plus POST /charges.

The first accepted request binds the key to canonical input and eventually to one outcome.

A matching replay receives the original outcome. A materially different request with that key is rejected.

04

Production example

A payment API receives POST /charges. The charge commits, but the HTTP response disappears in transit. The client sees a timeout and retries.

  • Same key and matching input: return the original charge rather than creating another.
  • Fresh key: the server sees a new logical operation and may create a second charge.
  • Same key but changed amount: reject the key/input conflict. Do not treat it as an update.
  • Same JSON but no shared key: payload equality alone cannot prove that the caller intends the same operation; two legitimate charges may have identical payloads.
05

Initial correctness invariants

  1. Within the declared scope and retention window, one key maps to at most one canonical request.
  2. One key produces at most one protected committed business effect.
  3. A valid replay returns an outcome consistent with the original committed operation.
  4. Reusing a key with materially different input is rejected rather than silently replayed or applied as an update.
Primary trade-off: longer retention and broader scope prevent more late duplicates and collisions, but increase storage, index, privacy/compliance, and operational costs. Decide using retry horizon, duplicate-effect severity, throughput, storage budget, compliance constraints, and key-collision assumptions.
06

Common mistakes

  • Equating a timeout with failure. A timeout means the result is unknown to the caller.
  • Calling key lookups “attempts.” Attempts are the original client request and its retry.
  • Using payload equality as operation identity. Identical payloads can represent separate valid operations.
  • Allowing same-key/different-input reuse to mutate the original operation.
  • Choosing scope and retention from storage cost alone while ignoring retry horizon and business risk.
